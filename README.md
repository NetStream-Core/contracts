# NetStream Contracts

Единый источник правды для того, как компоненты NetStream-Core общаются друг с другом: события в Kafka/ClickHouse, HTTP API `backend`. Не заменяет wire-формат (агент по-прежнему шлёт OTLP/protobuf, `backend` — обычный JSON HTTP) — фиксирует **смысл** полей поверх него, независимо от конкретной библиотеки-сериализатора.

Wire format и domain contract — разные вещи: можно сменить кодек с OTLP на что угодно другое, не меняя ни одного поля из `events/`.

## Состав

| Путь | Содержимое |
|---|---|
| `events/envelope.md` | Общие для всех событий поля: идентичность (`event_id`, `boot_id`, `sequence`) и две временные оси (`event_time`/`ingest_time`) |
| `events/flow.md` | `netstream.flow` — дельта по потоку за интервал съёма |
| `events/dns-query.md` | `netstream.dns.query` — один DNS-запрос с признаками |
| `events/blocklist-hit.md` | `netstream.blocklist.hit` — срабатывание блок-листа |
| `kafka/topics.md` | Топики Kafka: имена, кодировка, партиционирование, retention |
| `openapi/backend.yaml` | HTTP API control plane (`backend`): сенсоры, desired-конфиг, реестр моделей |

## Откуда взято и как поддерживать в актуальном состоянии

Схемы здесь списаны с уже реализованного и проверенного кода (`agent`, `deploy`, `backend`), а не придуманы заранее. Источник истины для реализации — сам код; этот репозиторий описывает то, что он делает, для тех, кто не читает все четыре репозитория сразу. При изменении контракта (новый атрибут события, новый эндпоинт) — правится один раз здесь и упоминается в PR того репозитория, который меняет поведение; синхронизация ручная, никакой генерации кода в эту сторону пока нет.

## Что сюда сознательно не входит

AsyncAPI-спецификация, JSON Schema для валидации на лету, версионирование схем через реестр (Schema Registry) — это уровень production-эксплуатации, который не нужен для одного агента и одной команды разработки. Если появится нужда — добавится тогда же.
